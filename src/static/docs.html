Hamro Pay API Integration

Accept UPI payments on your website, app or bot with three calls: create an order, send your customer to pay, then confirm the result from your server. Money goes straight to your own UPI account and Hamro Pay detects the payment automatically.

1 · Create orderYour server calls create-order and gets a payment_url.
2 · Customer paysThey pay the exact amount shown, from any UPI app.
3 · Auto-detectedHamro Pay spots the payment within seconds.
4 · You verifyCall order-status (or use a webhook) and check success.
01

Your API key

One key per account. It authenticates every developer API call.

  1. Log in to your Hamro Pay dashboard and open the Developer portal (available on every paid plan, BASIC and above).
  2. Click Generate API key. The key is created only when you ask for it, and starts with hmpay_.
  3. Copy it. Regenerate any time: the old key stops working immediately.
⚠
This is a different key from your dashboard login session. Treat it like a password: call the API from your server, never commit it to a public repository, and regenerate it if it leaks.

Before taking live payments

  • Connect a payment account (FamPay, Amazon Pay or Paytm MID) in the dashboard. Customers pay directly to your UPI.
  • Keep some Hamro Credits: commission is deducted from credits on every successful payment (plans with 0% commission need none).
  • Stay in Live mode (see Test & Live mode).

Authentication

      
Send the key in the JSON body as hamro_api, or as a header X-HamroAPI-Key (older x-api-key header also works). For GET calls use the header.

      
Rate limit

      
60 requests per 15 minutes per API key (per IP if no key is sent), shared across all endpoints.

Create Order

    
Creates a payment order and returns a payment_url to send your customer to.

yes
Amount in INR, at most 2 decimals. A plain number: 499, never "₹499" or "1,999". Minimum ₹1, maximum depends on your plan (see plans).

no
Shown on the payment page. Up to 100 characters. Default "Hamro Pay Payment".

10 digits, optionally prefixed with 91, +91 or 0. No spaces or dashes.

          
redirect_url
string
no
http(s) URL where the customer lands after paying. Hamro Pay appends ?hp_order=<id>&hp_result=success|failed. Never treat this as proof of payment.

          
useEmbedded
boolean
no
true for popup / in-app checkout (used by the widget). The page does not redirect.

        

        

        

        
ℹ
About pay_amount. Each waiting order is recognised by its exact amount. Your first pending order of ₹100 is exactly ₹100.00; if another ₹100 order is still waiting, the next becomes ₹100.01, ₹100.02 and so on (up to +₹0.49). Always show the customer pay_amount, not amount. An order stays payable for 15 minutes.

        
⚠
Most common cause of "Validation failed": sending amount as a formatted price string. Clean it first: Number(String(price).replace(/[^0-9.]/g,'')).

      

    

  


  

    
03
Order Status

    
Server-to-server check of an order. This is the only trustworthy proof of payment.

    

      
GET

      

        

          
Parameter
Type
Required
Description

          
orderId
path
always
The order_id returned by create-order, unmodified. You can only read your own orders.

          
X-HamroAPI-Key
header
always
Your API key.

        

        

        

        
status is always exactly one of pending, success or failed. On failed, reason is timeout (not paid in 15 minutes), cancelled (customer cancelled) or processing_failed. utr is returned only on success. Calling this endpoint also makes Hamro Pay check for the payment immediately, so it is safe to poll every 2.5 seconds or more.

        
⚠
Golden rule: a customer landing on your redirect_url, or a browser callback firing, is never proof of payment. Deliver the product only after your server sees status === "success" here.

      

    

  


  

    
04
Webhook Receiver

    
Get notified the moment a payment succeeds, so you don't have to poll.

    

      
Add your webhook URL(s) in the dashboard under Developer → Webhooks. Hamro Pay sends a POST with a JSON body to every saved URL when a payment succeeds. How many URLs you can add depends on your plan (BASIC 5, STARTER 10, GROWTH 25, BUSINESS 50, ADVANCE and ELITE unlimited).

      

        
Field
Type
Description

        
event
string
payment.success, or payment.test in Test mode.

        
order_id
string
Your order id (from create-order).

        
link_id
string|null
null for API orders; set when a payment-link was paid.

        
utr
string
Bank reference (UTR) of the payment.

        
amount
number
Amount the customer paid (pay_amount).

        
net_amount
number
Amount minus commission.

        
commission
number
Commission charged for this payment (taken from your Hamro Credits).

        
test
boolean
Only present (true) on payment.test events.

      

      

      
⚠
Deliveries are sent once, are not retried and are not signed. So never trust the body alone: re-check the order with Order Status before fulfilling, and make fulfilment idempotent (fulfil each order_id only once). Reply with HTTP 200 quickly.

    

  


  

    
05
Test & Live mode

    

      
Your account has one mode, switchable any time in the Developer portal. It applies to every create-order call.

      
    
        
  • Live: real UPI checkout and real money, paid directly to your UPI account.
    • 
        
  • Test: create-order returns a payment_url that opens a simulator with Success, Failed and Cancelled buttons. No money moves, your credits are untouched, and you need no connected payment account.
    • 
      

      
In Test mode pay_amount always equals amount. Nothing else changes shape: order-status returns the same values plus "mode": "test", and a simulated success sends a payment.test webhook.

      
⚠
Leaving Test mode on is the most common reason a "live" site stops taking real payments. If customers can't pay, check the mode first.

09
Best practices & security

    
    
      
  • Never trust a redirect or browser callback alone. Confirm with order-status from your server.
    • 
      
  • Create orders server-side and keep the API key out of public code.
    • 
      
  • Use the amount from your own database, never from the browser.
    • 
      
  • Make fulfilment idempotent. A webhook, a redirect and your own polling can all report the same payment.
    • 
      
  • Poll no faster than every 2.5 seconds and stay within 60 requests / 15 minutes per key.
    • 
      
  • Show the exact pay_amount. Paying a different amount will not be recognised automatically.
    • 
      
  • Regenerate the key immediately if you suspect a leak.
