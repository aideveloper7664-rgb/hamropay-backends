API Integration

Hamro Pay API Integration

Accept UPI payments on your website or app with three calls: create an order, send your customer to pay, then confirm the result from your server. Payments are detected automatically from your connected FamPay account.

1 · Create orderYour server calls create-order and gets a payment_url.
2 · Customer paysCustomer pays the exact amount shown, from any UPI app.
3 · Auto-detectedHamro Pay spots the payment in your FamPay emails within seconds.
4 · You verifyYour server calls order-status and checks success.
01

Overview & getting your key

Every Hamro Pay merchant account has exactly one API key (it starts with hmpay_). It authenticates every request you make.

Where to find it

  1. Log in to your Hamro Pay dashboard.
  2. Open the Developer section.
  3. Copy your key from there. You can regenerate it any time.

Before you take live payments

  • Connect a FamPay account (UPI ID + Gmail App Password). Payments are detected from that Gmail.
  • Keep some Hamro Credits. Commission is deducted from credits on every successful payment.
  • Stay in Live mode (see Test & Live mode).

Treat the key like a password

  • Call create-order from your server whenever you can. The browser widget is a quick-start convenience: it puts your key in page code.
  • Never commit it to a public repository.
  • If it leaks, regenerate it. The old key stops working instantly, with no grace period.

Create order

      
POST/api/developer/create-order

      
Creates a payment order and returns a payment_url for your customer. Send Content-Type: application/json.

      
FieldRequiredTypeNotes

        
hamro_apiYes*string*Not needed if you use the X-HamroAPI-Key header.

        
amountYesnumber₹1 to ₹5,000, at most 2 decimals. A plain number: 499, never "₹499" or "1,999".

        
titleNostringUp to 100 characters. Shown on the payment page. Default "Hamro Pay Payment".

        
customer_mobileNostring10 digits, optionally prefixed with 91, +91 or 0. No spaces or dashes.

        
redirect_urlNostringhttp(s) URL where the customer lands after paying. Hamro Pay appends ?hp_order=<id>&hp_result=success|failed.

        
useEmbeddedNobooleantrue for popup / in-app checkout (used by the widget). The page does not redirect.

      
ℹ
About pay_amount. Hamro Pay recognises each payment by its exact amount. Your first pending order is exactly amount (₹100.00). If another order of the same amount is still waiting, the next one becomes ₹100.01, then ₹100.02, and so on (up to ₹0.49 extra). The customer must pay the pay_amount shown on the payment page. You receive the full pay_amount (minus commission).

      
⚠
Most common cause of "Validation failed": sending amount as a formatted price string. Strip symbols and commas first: Number(String(price).replace(/[^0-9.]/g,'')).

      
200 / 201: order created
{
  "success": true,
  "message": "Order created",
  "data": {
    "order_id": "HP1792316718001ETM0",
    "payment_url": "https://your-hamro-frontend/pay/HP1792316718001ETM0",
    "amount": 100,
    "pay_amount": 100,
    "expires_at": "2026-10-18T10:45:00.000Z",
    "mode": "live"
  }
}

      
An order stays payable for 15 minutes. After that its status becomes failed with reason timeout.


      
Get order status

      
GET/api/developer/order-status/:orderId

      
Returns the current status. No body: orderId is the order_id from create-order. Send your key in the X-HamroAPI-Key header. You can only read your own orders. Calling this also makes Hamro Pay check your FamPay emails right away, so it is safe to call even if the customer closed the page.

      
200: status fetched
{
  "success": true,
  "message": "Status fetched",
  "data": {
    "order_id": "HP1792316718001ETM0",
    "status": "success",
    "amount": 100,
    "pay_amount": 100,
    "utr": "629040332216",
    "mode": "live"
  }
}

      
status is always exactly one of "pending", "success" or "failed". When it is failed, an extra reason field tells you why: timeout (not paid in 15 minutes), cancelled (customer pressed cancel) or processing_failed (payment seen but could not be credited, for example no Hamro Credits left). utr is included only on success.

      
⚠
The most important rule in this document: a customer arriving at your redirect_url, or a browser callback firing, is never proof of payment. Always call order-status from your server and check status === "success" before you fulfil anything.

    

  


  

    
03
Webhooks (optional)

    

      
Set a webhook URL in the dashboard (Developer section). Hamro Pay sends a POST with a JSON body when a payment succeeds, so you don't have to poll.

      
payment.success
{
  "event": "payment.success",
  "order_id": "HP1792316718001ETM0",
  "link_id": null,
  "utr": "629040332216",
  "amount": 100,
  "net_amount": 98,
  "commission": 2
}

      
  • link_id is null for API orders, and set for payment-link payments.
  • In Test mode the event is payment.test with "test": true and no money moves.
  • Deliveries are sent once and are not retried, and they are not signed. Treat a webhook only as a hint: confirm with order-status before fulfilling.

06
Test mode & Live mode

    

      
Your account has one mode, switchable any time in the dashboard (Developer section). It applies to every create-order call. New accounts start in Live.

      
    
        
  • Live: real UPI checkout, real money, wallet credited.
    • 
        
  • Test: create-order returns a payment_url that opens a simulator with three buttons: Success, Failed, Cancelled. No money moves, your wallet and credits are untouched, and test orders do not appear in Payment History.
    • 
      

      
In Test mode you don't need a FamPay account, credits or wallet room, and pay_amount always equals amount. Nothing else changes shape: order-status returns the same pending / success / failed values (plus "mode": "test"), so the code you write for testing is the code you ship.

      
⚠
Leaving Test mode on is the most common reason a "live" site stops taking real payments. If customers can't pay, check the mode in your dashboard first.

    

  


  

    
07
Best practices & security

    
    
      
  • Never trust a redirect or browser callback alone. Confirm with order-status from your server.
    • 
      
  • Create orders server-side and keep the API key out of public code.
    • 
      
  • Use the amount from your own database, never from the browser, when you call create-order.
    • 
      
  • Make fulfilment idempotent. A webhook, a redirect and your own polling can all report the same payment. Fulfil each order_id only once.
    • 
      
  • Poll no faster than every 2.5 seconds and stay within 60 requests / 15 minutes per key.
    • 
      
  • Show the exact pay_amount. Paying a different amount will not be recognised automatically.
    • 
      
  • Regenerate the key immediately if you suspect a leak.
